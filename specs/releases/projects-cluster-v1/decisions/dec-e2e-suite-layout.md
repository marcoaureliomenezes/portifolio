# Decision — E2E suite layout for /projetos/*

**Status:** Aprovado
**Date:** 2026-05-17
**Owner:** product-engineer
**Release:** projects-cluster-v1
**Blocks:** T-PC-C-08 (E2E activation)

## Context

After landing Phase A + Phase B of `projects-cluster-v1`, two E2E suites covered the
same surface area (`/projetos`, `/projetos/:slug`) in `frontend/tests/e2e/`:

1. **`frontend/tests/e2e/projects-cluster/` (canonical)** — 9 files, 37 test cases
   numbered `PC-E2E-01..37`, predate the release migration. Comprehensive: index,
   layout-shell, a11y, i18n, nav, three detail templates (case-study/meta/games),
   tauan-games link-out.
2. **`frontend/tests/e2e/*.spec.ts` (root duplicates)** — 6 files added by T-PC-C-01
   (`projects-index`, `project-detail-case-study`, `project-detail-meta`,
   `project-detail-games`, `tauan-games-link-out`, `nav-projects`). Use a different
   numbering (`PC-INDEX-*`, `PC-CS-*`, `PC-NAV-*`, `PC-LINKOUT-*`). All `test.skip`.

Both sets cover identical Acceptance Criteria (AC-PC-04, AC-PC-08, AC-PC-11, AC-PC-12,
AC-PC-13, AC-PC-16). Both depend on the same `fixtures/routes.ts`. The duplication
creates ambiguity for T-PC-C-08 ("which set do we activate?") and for future drift
("which numbering is canonical?").

## Decision

**Delete the 6 root-level stubs. Keep `frontend/tests/e2e/projects-cluster/` as the
single canonical suite for the projects cluster.**

### Rationale

1. **Coverage breadth.** `projects-cluster/` has 37 tests across 9 files including
   a11y (PC-E2E-27..31) and layout-shell (PC-E2E-32..37). The root set covers only
   the 6 ACs explicitly listed in T-PC-C-01 and omits a11y + layout-shell entirely.
2. **Pre-existing structure.** The `projects-cluster/` subdirectory predates the
   release model and was authored as a deliberate qa-engineer artifact. The root
   stubs were generated by T-PC-C-01 without checking that the canonical suite
   already existed.
3. **Numbering coherence.** `PC-E2E-NN` is a single sequence across all files;
   easier to reference in reports and CLOSURE evidence than mixed
   `PC-NAV-*`, `PC-INDEX-*`, `PC-CS-*`.
4. **No unique coverage lost.** Every test ID in the root set has a 1-to-1
   equivalent in `projects-cluster/` covering the same AC and selector intent.
   Verified by manual comparison of test descriptions.
5. **Single root for E2E** is preserved for non-projects specs already under
   `pages/` (home, language-switch, deep-link, etc.) — `projects-cluster/`
   becomes the canonical sibling for everything `/projetos/*`-scoped.

### Scope boundary (going forward)

- `frontend/tests/e2e/projects-cluster/**` → tests for `/projetos`, `/projetos/:slug`,
  and any nav/CTA path that leads into the cluster (Header "Projetos" link,
  Hero 3rd CTA).
- `frontend/tests/e2e/pages/**` → tests for the rest of the site (home, contact,
  language switch, CV download, NotFound).
- `frontend/tests/e2e/fixtures/**` → shared routes/data constants (route map).

New tests for the projects cluster must live in `projects-cluster/` and follow the
`PC-E2E-NN` numbering. New tests for other features must live in `pages/` and follow
that subdir's existing patterns.

## Files deleted

- `frontend/tests/e2e/nav-projects.spec.ts`
- `frontend/tests/e2e/projects-index.spec.ts`
- `frontend/tests/e2e/project-detail-case-study.spec.ts`
- `frontend/tests/e2e/project-detail-meta.spec.ts`
- `frontend/tests/e2e/project-detail-games.spec.ts`
- `frontend/tests/e2e/tauan-games-link-out.spec.ts`

## Impact on T-PC-C-08

T-PC-C-08 activates the 37 tests in `projects-cluster/` (remove `test.skip`), not the
deleted duplicates. The task description in `TASKS.md` references "6 spec files" — this
must be amended to "9 spec files in `projects-cluster/` covering 37 test cases" when
the task is started.

## Reversibility

If a future qa-engineer audit identifies a coverage gap unique to a deleted stub, the
test can be ported into the matching `projects-cluster/` file. Git history preserves
the deleted content (commit referenced in the deletion).
